# 0017 · Phase 3 在 Phase 2 等待验收期间开工

**状态：** 已采纳（2026-11-18）。所有者批准，条件是"不影响结果"：Phase 3 的工作不能改变 Phase 2 剩余两项验收的结论。下面"约束"一节就是这个条件的具体做法。

## 背景

路线图的排序原则第 3 条是"达标才进下一阶段"，工作守则原来写的是 Phase 2 的 2.3 和 2.10 两项验收都通过之后才开始 Phase 3。到 2026-11-18，Phase 2 只剩两项验收，而且都只能等：

- **2.3**：录制类数据源连续 14 天自动入库，观察窗口到 2026-11-30 00:00 UTC。
- **2.10**：两份快照（Deribit 盘口摘要、Hyperliquid）的第一个完整月份是 11 月。工作流"录制类规范层"（`.github/workflows/recorded.yml`）每月 4 日 06:19 UTC 才写上个月，因为月末之后还要等 `settle_days` 天（`config/recorded.toml`，2 到 3 天）。所以写入和重建核对最早在 2026-12-04。

真正卡住 Phase 3 的是 2.10，不是 2.3。就算缩短 2.3 的窗口，Phase 3 也不会提前一天。窗口本身也不该缩短：以 11-17 的每 4 小时采集为例，6 次里 GitHub 自己的定时只启动了 3 次，另外 3 次靠 11-15 才加上的补跑（`src/finresearch/schedules.py`）补上；11-16 还出现过一次 DVOL 采集失败，后来自己恢复。这些正是 14 天要观察的东西。

另一方面，Phase 3 不需要这两项验收要检验的数据：

- 统计工具箱、噪声工厂、植入效应的合成数据，都只用合成数据。
- 用到真实数据的部分（噪声工厂按真实数据校准厚尾和相关结构、加密横截面动量的阳性对照）用的是 U1，它已经在 2.5 验收过。
- 没有一项要读 2.3 正在录的两份快照。

这些等待只花日历时间，不花工作量。按原规则，这段时间 AI 会话只能闲着。

## 选项

- **(a) 照原规则等到 2.3 和 2.10 都通过。** 最保守，Phase 3 最早 2026-12-04 之后开工。
- **(b) 缩短 2.3 的观察窗口。** 换不来时间（2.10 才是卡点），还削弱了对补跑机制的检验。
- **(c) Phase 3 现在开工，加约束保证不影响 Phase 2 的验收；把门槛从"开工"挪到"验收"（采纳）。**

## 决定

(c)。Phase 2 只剩被动验收时，Phase 3 的步骤可以先做。Phase 2 两项验收都通过之前，Phase 3 不能宣告验收，也不能据它定稿[科研规程](../protocol.md)第 5 节的阈值。

## 约束

在 2.3 和 2.10 两项验收都通过之前，Phase 3 的工作遵守下面五条。每一条都对着一种具体的影响方式：

1. **不启动 Phase 2 的工作流。** 观察窗口里不手动启动采集；补跑照常由系统自己启动。2.10 的核对在 2026-12-04 写入之后按验收要求进行，与 Phase 3 无关。
2. **只新增文件，不改录制和加工用到的已有文件。** 所有定时工作流都从 `main` 运行同一个 `finresearch` 包：改了已有的模块、命令行入口（`src/finresearch/cli.py`）、`config/` 或 `.github/workflows/` 里的文件，下一次采集就跑新代码。所以 Phase 3 的拉取请求只新增模块、测试和文档；不改 `src/`、`config/`、`.github/workflows/` 里已有的文件。工具先以库函数加测试交付，命令行入口等两项验收通过后再接。确实需要改已有文件的，等验收通过后再做。
3. **不改已锁定依赖的版本。** 内容指纹是对 Arrow 数据的字节求的（`src/finresearch/data/table.py` 的 `fingerprint`），2.10 的重建核对要求同一份原始响应加工出同样的字节；依赖升级可能让已写入的月份核对不一致，而原因与数据无关。可以新增依赖，但 `uv.lock` 的差异里，已有的包版本一个都不能变。
4. **不在 GitHub Actions 上跑读写数据集的任务。** Hugging Face 每个仓库每小时最多 128 次提交，超过就回 429（[架构](../architecture.md) 7.3 的实测）；录制的推送和 Phase 3 的推送用的是同一个数据集。GitHub 免费账户同时最多运行 20 个任务，超出的排队（[GitHub 文档](https://docs.github.com/en/actions/reference/usage-limits-billing-and-administration)；本仓库所属账户是什么套餐没有核实）。所以这段时间 Phase 3 只跑持续集成里的单元测试和合成数据，不读写数据集、不开并行的运算任务。
5. **Phase 2 优先。** 任何一项验收没通过，先修 Phase 2，Phase 3 暂停到修好为止；如果要重新开观察窗口，新窗口里这五条照样适用。

两项验收都通过后，这五条自动解除，交接页和路线图同时更新。

## 代价

- "达标才进下一阶段"只在开工这一端放松。万一 Phase 2 验收失败，要同时照顾两条线；按第 5 条，Phase 2 先修。
- 约束 2 让 Phase 3 早期的代码暂时没有命令行入口，要等验收之后补一个小的拉取请求。

## 重新考虑的条件

- 以后某个阶段末尾同样只剩被动验收，可以援引本条，但要重新核对下一阶段确实用不到被验收的数据，并写明对应的约束。
- 如果发现 Phase 3 的某一步确实要用 2.3 正在录的数据，那一步等两项验收通过后再做。
