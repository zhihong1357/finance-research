# 0026 · 所有者怎样使用系统：使用手册、固定格式的简报、Telegram 单向通知

**状态：** 已采纳（2026-11-19）。所有者在会话中选了推荐的两项：Telegram 单向通知加聊天简报；Telegram 在 11-30 观察期结束、2.3 核对完之后再做。

## 背景

所有者是初学者，不在本地运行任何东西。到目前为止，所有者接触项目只有三条路：合并拉取请求、回答 AI 提出的决定、收数据中断问题的邮件。没有一个地方能一眼看清"现在怎样、我要做什么"，也没有一份文档讲清楚这个系统最后怎么用。所有者提出要一个对新手友好的交互方式，并问 Telegram 机器人是不是好主意。

两个限制：

- 研究结论的数字由第三方数据得出，不能进公开仓库（[决策 0008](0008-derived-results.md)），也不应该发到第三方聊天服务。
- Phase 2 验收之前，[决策 0017](0017-phase-3-during-phase-2-acceptance.md) 的约束有效：不改已有的代码、配置和工作流，不在 GitHub Actions 上读写数据集。

## 决定

给所有者看的东西分三层，每层的要求不同。

1. **报警**：出了事、要所有者动手时才推送，平时安静。报警必须由固定的程序发出，不依赖 AI。AI 额度用完时，报警照样要到。
2. **定期报告**：每周一份，格式固定，两分钟读完。
3. **问答与解释**：所有者想知道细节时，直接在 Claude 里问。

具体做法：

- **使用手册**（[`docs/owner-guide.md`](../owner-guide.md)）：系统最后交给所有者什么，每个阶段所有者做什么，怎样判断结论能不能信，常见问题。现在就写。
- **固定格式的所有者简报**（[`docs/owner-brief.md`](../owner-brief.md)）：所有者说"汇报"时，AI 按同一格式回答，共五段：一句话现状、红绿灯、要你做的事、接下来、不要做。Claude Code 通过 `.claude/skills/owner-brief/`，Codex 通过 `AGENTS.md`，用的是同一份格式。现在就写。
- **Telegram 单向通知**：只发不收。GitHub 开出"数据中断"问题时立刻推一条，关闭时推"已恢复"；每周一推一份周报，内容是运行成功和失败的次数、待合并的拉取请求、打开的问题、下一个日期。用一个新的工作流来发，不改已有的工作流，不读写数据集，不调用 `finresearch` 的代码。令牌和 chat id 只存 GitHub Secrets，日志里不打印。2.3 在 11-30 核对完之后做。

## 为什么这样分

- 报警和报告分开，是值班和运维的通行做法：报警太多，人就不看了。
- 报警不交给 AI：AI 会话可能因为额度用完而不运行。所有者另一个项目的定时任务 2026-11-16 就是这样没跑成的。
- 问答交给 AI：Claude App 能读仓库、能解释，比只认固定命令的机器人更适合初学者。

## 不做的事

- **Telegram 双向机器人**（在 Telegram 里打字问答、下命令）：要一台一直在线的服务器，和"一个人维护、简单优先"冲突；令牌泄露后别人能借它操作；问答这件事 Claude App 已经做得更好。
- **网页应用或看板服务**：要新代码、新托管、新密钥，而且现在还没有结论可以展示。
- **把研究数字发到 Telegram**：Telegram 机器人的消息不是端到端加密的，而且数据条款不允许公开传播由第三方数据得出的结果。

## 代价

- 所有者要自己在 Telegram 建一个机器人，再把两个值存进 GitHub Secrets（手册会写一步步的说明）。
- 多了一个工作流要维护。它出错不会影响采集，因为它独立运行，也不碰数据集。
- 周报由程序拼出来，不如 AI 写的生动。要解释，就去 Claude 里问。

## 什么时候重新考虑

- 仓库转为私有之后（[决策 0002](0002-repo-visibility.md)：Phase 4 结束前保持公开），结论卡和配置建议可以有一个私有的展示页。
- Telegram 在所有者所在的地区不可用，或者有更合适的推送渠道时。
