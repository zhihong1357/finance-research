# 落地顺序

## 当前状态

**Phase 0 · 奠基**，等待所有者确认文末的三项决定。之后进入 Phase 1 · 骨架。

## 排序原则

1. **事后补不回来的先做。** 试验记录、数据的时间语义、原始数据的保存，错过了无法重来。算法和模型随时可以加。
2. **达标才进下一阶段。** 每个阶段都有验收标准，写成可以检查的事实。
3. **每个阶段结束时，系统都能完整跑通一遍。** 先做一条贯穿各层的细线，再逐层加宽。
4. **不赶时间。** 本文不给日期，只给顺序和标准。

## 总览

| 阶段 | 做什么 | 完成的标志 |
|---|---|---|
| 0 奠基 | 总纲、规程、架构、决策记录 | 所有者确认三项决定 |
| 0.5 止损 | 开始保存原始期权链 | 每个交易日的原始文件都在 |
| 1 骨架 | 工程底座、时间语义、溯源、注册表、时点查询 | 一条命令重现一份完整报告；前视和漏记账会被自动拦住 |
| 2 数据平台 | 存储、采集器、质量检查、监控 | 首批数据源连续 14 天自动入库 |
| 3 推断工具箱与元研究 | 统计工具、噪声工厂、阳性对照 | 量出整条流程的误报率和检出率，阈值定稿 |
| 4 模拟与成本 | 回测引擎、成本模型、容量分析 | 与手算和旧引擎逐笔对账一致 |
| 5 研究项目 | 按规程逐个开展 | 每个项目至少一个假说走完全程并入库 |

## Phase 0.5 · 止损：现在就保存原始期权链

这是整份计划里唯一有时间压力的事。

**问题。** `orderflow` 仓库里的录制器每天读取 CBOE 的期权链，算出几个指标存下来，原始期权链没有保存。CBOE 的接口只提供当前快照，当天不存，以后就找不回。将来如果想换一种方式计算 GEX，或者研究现在没想到的问题，没有原始数据就无从做起。

`fakeout-backtest` 对 Deribit 的做法是对的：每天保存全量期权快照，从 2026-10-26 起已有记录。

**做法。** 在 `orderflow` 的录制步骤里加一步，把 SPX、SPY、QQQ、IBIT 四个标的的原始期权链压缩后存进 `lab-data` 分支。实测合计约 3.5 MB/天。这是过渡方案，Phase 2 的数据平台建成后接管并导入这些文件。

**验收。** 每个美股交易日，四个标的的原始文件都存在且能正常解压读取。

## Phase 1 · 骨架

**目标。** 建成治理层和内核库的最小可用版本，使[总纲](charter.md)里"事后补不回来的三样东西"从第一天起就被正确处理。

**步骤。** 每一步是一次独立的、可审查的提交。

| 步骤 | 内容 |
|---|---|
| 1.1 工程底座 | 目录结构、依赖锁定、代码风格与类型检查、测试框架、持续集成 |
| 1.2 时间与标识 | 带时区的时间类型、交易日历、品种标识方案 |
| 1.3 溯源 | 内容指纹、运行清单、配置指纹、结果指纹 |
| 1.4 注册表 | 五类文件的格式定义、校验命令、"只追加"检查 |
| 1.5 时点查询 | 在仓库内的小型测试数据集上实现，包含时钟上限、三段边界和金库令牌 |
| 1.6 贯穿各层的细线 | 合成数据（由代码按固定种子生成，模仿一个真实数据源的格式，带三个时间，含一次修订）→ 原始层 → 规范层 → 时点查询 → 一个登记的示例假说 → 一次运行 → 账本记录 → 标准报告 |

**验收。**

- 持续集成全部通过。
- 一条命令从空白状态重现 1.6 的报告，结果指纹与仓库里记录的一致。
- 故意写一段前视代码，测试失败。
- 故意删掉一条账本记录，持续集成失败。
- 故意越过金库边界查询，程序报错并留下记录。

**不做。** 不接入远程存储，不写真实的采集器，不做任何真实研究。细线用合成数据，所以 Phase 1 不涉及任何第三方数据的存放问题。

## Phase 2 · 数据平台

**目标。** 让数据持续、自动、可追溯地流入，并在出问题时有人知道。

**产出。**

- 存储后端（见决策记录 0003）。
- 首批采集器：

| 类别 | 数据源 |
|---|---|
| 宏观与利率 | FRED（含历史公布版本）、纽约联储 SOFR |
| 波动率与期权 | CBOE 期权链、CBOE VIX 历史、Deribit 期权与期货 |
| 加密衍生品 | OKX、Hyperliquid、Deribit 的资金费率；Binance 公开数据站的 K 线、逐笔成交、持仓量 |
| 持仓 | CFTC 持仓报告 |
| 价格 | Yahoo 的指数、期货、ETF 日线 |

- 旧录制数据的导入：`fakeout-backtest` 的 Deribit 期权快照，`orderflow` 的 `gex-data` 和 `lab-data` 分支。
- 数据源目录：每个数据源的地址、时间语义、限流、使用条款摘要、已知问题。
- 数据质量检查：格式、取值范围、新鲜度、多数据源之间的相互核对。
- 监控与通知。
- 历史回补：有历史可取的数据源一次补齐。

**验收。**

- 首批数据源连续 14 天自动入库，期间没有人工干预。
- 任何一个数据源中断，24 小时内收到通知。
- 删除规范层之后，能由原始层完整重建，内容指纹一致。
- 每张表都有数据字典。

**开始前要查清的事** 见[架构](architecture.md)第 6.4 节。

## Phase 3 · 推断工具箱与元研究

**目标。** 在用这套系统研究市场之前，先研究这套系统本身：它会不会把噪声当成发现，能不能找到真实存在的效应。

**产出。**

- 统计工具箱。迁移 `orderflow` 的 `lab/stats`，并补充：多重检验校正、平稳自助法、带清洗和禁区的交叉验证、功效计算。
- 噪声工厂。生成没有任何优势的合成数据，同时保留真实数据的厚尾和波动聚集。
- 植入效应的合成数据。在噪声里埋入已知大小的效应。
- 阳性对照。在真实数据上复现一到两个被文献反复确认的效应，候选是"股指的隐含波动率长期高于实现波动率"。

**验收。**

- 在纯噪声上，整条流程（从探索到结论）的误报率不高于名义水平。
- 给出不同效应大小和数据长度下的检出率曲线。
- 阳性对照复现成功。
- [科研规程](protocol.md)第 5 节的阈值据此定稿。

## Phase 4 · 模拟与成本

**目标。** 一个可信的回测引擎，以及贴近现实的成本模型。

**产出。**

- 事件驱动的回测。沿用 `orderflow` 的成交规则：市价单以下一根 K 线开盘价成交，限价单必须被价格穿过才算成交。
- 成本模型：手续费、滑点、资金费率、冲击成本。
- 容量分析：一个策略在多大资金量下优势被自身的交易成本吃掉。

**验收。**

- 一组手算的场景，逐笔结果一致。
- 与 `orderflow` 引擎在同一批订单上对账一致。
- 成本为零、正常、加倍三种情形的结果都能一键得到。

## Phase 5 · 研究项目

**目标。** 按规程开展真正的研究。

**顺序。**

| 顺序 | 项目 | 排在这里的理由 |
|---|---|---|
| 5.0 | 旧策略复审 | 假说现成；结论直接决定是否继续在这条线上投入；也是整套系统的第一次实战 |
| 5.1 | P3 空间关系 | 机制最清楚，成本模型最明确，数据已经在录 |
| 5.2 | P2 波动率与期权流 | 依赖录制数据的积累；先回答"GEX 能否预测实现波动率" |
| 5.3 | P1 宏观与流动性 | 用历史公布版本重做四层水晶球的检验 |
| 5.4 | P4 订单流 | 数据量最大，对工程的要求最高 |

**验收。** 每个项目至少有一个假说走完整个生命周期并入库。结论是"支持"还是"不支持"都算完成。

## Phase 6 · 配置与仓位

**目标。** 把结论库变成配置建议。

**产出。**

- 所有者的目标与约束文件，包括能承受的最大回撤。
- 基准组合：低成本、分散。任何主动的想法都要先赢过它。
- 仓位规则：只有 E4 以上的结论参与，仓位按优势估计的不确定度折算。
- 回撤控制规则。

**验收。** 给定结论库和约束，系统输出配置建议及其依据，并通过历史压力情景的检验。

---

## Phase 7 · 模拟盘

**目标。** 在不动用资金的情况下，取得前向证据。

**产出。** 前向运行的模拟盘，每个策略带预先登记的停止规则。

**验收。** 运行长度达到事先算好的最短长度，实际表现落在预期分布之内（证据等级 E5）。
